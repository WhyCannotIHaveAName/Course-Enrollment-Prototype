# EnrollmentLab 需求说明

> 本文档只记录实现第一版所需的最小需求。它不是对 SJTU GC 现行选课规则的完整说明。

## 1. 项目目标与边界

EnrollmentLab 是一个以学习为目的的课程分配与并发控制实验平台。项目参考对 SJTU GC 选课流程的实际观察，使用合成数据复现其中一部分业务，并尝试研究并发正确性和分配机制。

第一版需要实现：

- 学生、课程、教学班、选课轮次和时间段的数据存储；
- 容量、先修课、时间冲突和学分规则检查；
- Lucky Draw 和 Early Bird 两种选课模式；
- 选课、退课、请求重试与最终结果查询；
- Override 申请、管理员处理和审计日志；
- 简单课表预览；
- 并发正确性测试、负载测试和基础性能指标。

第一版暂不实现：

- 真实统一身份认证、真实学生数据或学院账号连接；
- 与学校现有系统、Canvas、邮箱或微信同步；
- 多平台客户端和复杂前端 GUI；
- 完整的真实选课规则，例如 Co-requisite、重修、小学期特殊规则和完整课程目录；
- Waitlist；
- 对真实 GC 系统后台实现或性能瓶颈的推断。

如果未来把系统部署到公开网络，应补充 HTTPS、身份认证和更完整的安全设计；这些不属于第一版本地原型的目标。

## 2. 规则信息的可信度

本文使用三种标记：

- **实际观察**：来自项目作者对 GC 学生端流程的实际使用观察，但不代表已经了解后台实现；
- **原型决定**：为使第一版边界清楚、可以实现和测试而自行设定的规则；
- **尚未确定**：目前没有足够证据或尚未作出决定。

实际观察只用于描述可见行为。除非有进一步证据，否则不能由界面表现推断后台使用了数据库锁、消息队列或其他具体技术。

## 3. 参与者

### 学生（Student）

学生是普通用户，可以参加选课轮次、提交或撤回选择、查看结果、退课、申请 Override 和查看自己的课表。

### 管理员（Supervisor）

管理员是具有额外权限的管理角色，可以创建、发布、启动和结束选课轮次，处理 Override，修改教学班容量，并查看选课情况与审计记录。

管理员的敏感操作必须记录操作者、时间、原因以及修改前后的状态。

## 4. 核心术语

### Course

课程本身，例如某一门“微积分”。每门 Course 具有唯一课程编号、名称、学分和可能存在的先修要求。

第一版将“已经完成某 Course 的学生不能再次选择该 Course”作为**原型决定**，不将其声称为完整的 GC 重修规则。

### Section

某门 Course 在特定学期实际开设的教学班。同一 Course 可以有多个 Section，每个 Section 具有容量和上课时间。

学生成功选入某个 Section 后，该 Course 的学分计入本学期选课学分；这不表示学生已经完成课程或获得最终学分。

### Enrollment Round

一轮具有模式、开放时间、结束时间和适用学生范围的选课活动。模式为 Lucky Draw 或 Early Bird。

实际 GC 流程中可观察到以下大致顺序：

1. Lucky Draw 1（大一学生除外）；
2. Lucky Draw 2（大一学生除外）；
3. 仅面向大一学生的 Lucky Draw；
4. Early Bird 1；
5. Early Bird 2。

第一版采用**原型决定**：不把以上五轮硬编码成固定自动序列。管理员可以自行创建和启动 Enrollment Round，并配置模式与适用学生范围。

### Choice

学生在 Lucky Draw 中放入选课篮、但尚未正式提交的 Section 选择。Choice 可以在轮次结束前修改，不代表已经参加抽签，也不占用 Section 容量。

### Submission

学生点击 Submit 后形成的一次 Lucky Draw 正式申请。系统保留该学生最后一次有效提交的选择快照。

Submission 表示学生参加抽签，但不代表已经成功选课，也不占用 Section 容量。

### Sign-up Request

学生在 Early Bird 中点击 Sign Up 后发出的选课请求。系统检查规则并处理请求，成功时产生 Enrollment，失败时返回明确原因。

“系统处理请求”不预设后台一定使用队列或任何特定并发方案。

### Enrollment

学生最终成功选入某个 Section 后形成的有效选课关系。只有有效 Enrollment 才占用 Section 容量，并计入学生当前选课学分。

### Override Request

学生针对正常规则不允许的操作提出的例外申请，例如超出学分上限、不满足先修要求或发生时间冲突。管理员可以批准或拒绝申请，并必须填写原因。

第一版把不同类型的例外统一建模为 Override Request，不复刻 GC 可能存在的全部分类和流程。

### Audit Log

对敏感操作形成的不可无痕修改的记录，至少包含操作者、操作时间、操作原因、对象以及修改前后的状态。

## 5. 两种选课模式的状态流程

### 5.1 Lucky Draw

```text
Choice（选课篮）
    ↓ Submit
Submission（正式抽签申请）
    ↓ 轮次结束后执行抽签
Enrollment（抽中）或 Not Selected（未抽中）
```

根据实际观察：

1. 学生把 Section 加入选课篮时，系统检查先修条件、时间冲突和学分上限；
2. 学生点击 Submit 时，系统检查学分下限；
3. 在轮次结束前，学生可以修改选课篮并重新提交，系统只保留最后一次有效 Submission；
4. 轮次结束后，不再接受新的 Submission；
5. 申请人数不超过容量时，所有有效申请者都可成功；申请人数超过容量时，系统随机选择人数填满容量；
6. 抽签成功才产生 Enrollment。Choice 和 Submission 均不增加已录取人数；
7. 学生最终抽中的课程可能少于提交的课程，因此最终选课学分可能低于提交时要求的学分下限。

第一版采用**原型决定**：学分下限只作为 Submission 的提交条件。抽签后学分低于下限不视为系统违反不变量。

### 5.2 Early Bird

```text
Sign-up Request
    ↓ 规则检查与并发处理
Enrollment（成功）或 Rejected（失败）
```

根据实际观察：

1. Early Bird 没有统一的 Submit 步骤；
2. 学生点击某个 Section 的 Sign Up 后，系统检查先修条件、时间冲突和学分上限；
3. 检查和容量条件满足时，请求成功并产生 Enrollment；
4. Section 已满时，新的请求不能直接产生 Enrollment。

Early Bird 如何执行学分下限检查目前为**尚未确定**。可能与 Drop 操作有关，也可能存在尚未观察到的其他流程。第一版的具体规则将在实现退课前另行决定。

### 5.3 Drop

```text
Enrollment → Dropped
```

Drop 成功后，Enrollment 不再有效，Section 的已录取人数减少。Drop 时是否必须立即满足学分下限属于**尚未确定**的问题。

## 6. 第一版业务规则

| 编号 | 规则 | 状态 | 生效时刻 |
| --- | --- | --- | --- |
| BR-01 | Choice 和 Submission 不占用 Section 容量，只有有效 Enrollment 占用容量 | 原型决定 | 创建或更新相应对象时 |
| BR-02 | Lucky Draw 加入 Choice 时检查先修、时间冲突和学分上限 | 实际观察 | 加入或更新 Choice 时 |
| BR-03 | Lucky Draw 提交时检查学分下限 | 实际观察 | 创建有效 Submission 时 |
| BR-04 | Lucky Draw 每名学生只保留最后一次有效 Submission | 实际观察 | 学生重新提交时 |
| BR-05 | Lucky Draw 结果可能低于学分下限，第一版不自动补救 | 原型决定 | 抽签完成时 |
| BR-06 | Early Bird 没有统一 Submit，Sign-up 成功后直接产生 Enrollment | 实际观察 | Sign-up Request 成功时 |
| BR-07 | 同一学生不能同时选入同一 Course 的多个 Section | 原型决定 | 创建 Enrollment 时 |
| BR-08 | 已完成某 Course 的学生不能再次选择该 Course | 原型决定 | 添加 Choice 或发起 Sign-up 时 |
| BR-09 | 管理员可以修改已发布 Section 的容量，但新容量不得低于当前有效 Enrollment 数量 | 原型决定 | 修改容量时 |
| BR-10 | 容量修改、Override 处理等敏感管理员操作必须写入 Audit Log | 原型决定 | 敏感操作提交时 |
| BR-11 | 第一版不在扩容后自动重新抽签或自动处理 Waitlist | 原型决定 | 修改容量后 |

## 7. 核心不变量

以下条件必须由代码、数据库约束和自动化测试共同保护：

1. 对于任何 Section：`active_enrollment_count <= capacity`；
2. 同一学生不能拥有两条指向同一 Section 的有效 Enrollment；
3. 同一学生不能同时拥有同一 Course 下多个 Section 的有效 Enrollment；
4. 除非存在已批准的 Override，有效 Enrollment 之间不得发生时间冲突；
5. 除非存在已批准的 Override，创建 Enrollment 时必须满足适用的先修要求和学分上限；
6. 同一个选课或退课请求被重复提交，不能产生重复 Enrollment 或重复释放容量；
7. Enrollment、容量占用结果和相应审计记录不能出现只提交一部分的状态；
8. 所有管理员敏感操作都必须有对应 Audit Log；
9. 相同输入、规则版本和随机种子必须产生相同的 Lucky Draw 结果。

学分下限没有被写成“任何时刻都成立”的全局不变量，因为 Lucky Draw 的最终结果可能低于提交时的学分下限。

## 8. 尚未确定的问题

1. Early Bird 在什么时刻、以什么方式处理学分下限？
2. Drop 是否应在操作时检查学分下限？如果检查，尚未达到下限的学生如何进行换课？
3. Override Request 的状态和最小审批流程应如何设计？
4. Lucky Draw 的“随机”在第一版中采用什么具体算法和公平性定义？
5. 管理员在 Lucky Draw 完成后增加容量时，新增名额应如何处理？第一版暂不自动处理，但需要明确用户可见行为。
6. Waitlist 是否在后续版本加入，以及采用先进先出还是其他顺序？

这些问题不会被默认猜测。它们将在相关模块开始实现前转化为明确的原型决定。
