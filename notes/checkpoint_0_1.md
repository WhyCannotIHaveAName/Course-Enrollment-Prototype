## 第 0.1 课：需求、业务规则与不变量

### 一、我们现在在做什么？

写程序之前，必须先回答：

> 这个系统接受什么输入？允许什么行为？必须保证什么永远不会出错？

如果直接开始写代码，很容易出现这种情况：

- 数据库已经设计好了，后来才发现无法表示候补状态；
- “退课后学分低于下限”究竟允许还是拒绝，没有人确定；
- Lucky Draw 写完了，却说不清什么结果算正确；
- 测试只能证明程序能运行，不能证明业务逻辑正确。

因此，检查点 0 的第一部分不是“写页面”，而是把模糊想法变成可以实现、可以测试的规则。

---

## 1. 什么是需求？

需求描述的是：

> 系统需要做什么，或者系统需要具备什么性质。

需求主要分成两类。

### 功能需求

描述系统能够执行的行为。

例如：

- 学生可以查看教学班；
- 学生可以提交选课请求；
- 管理员可以批准 override 工单；
- 系统可以运行 Lucky Draw。

它回答的是：

> 系统能做什么？

### 非功能需求

描述系统工作的质量或限制。

例如：

- 并发选课时不能超出容量；
- Lucky Draw 结果必须可以复现；
- 所有管理员介入必须可以审计；
- 在某种测试环境中，95% 的请求应在一定时间内完成。

它回答的是：

> 系统必须做得多可靠、多快、多安全或多容易维护？

“系统支持选课”是功能需求；“即使一百人同时选课也不能超选”则是正确性方面的非功能需求。

---

## 2. 什么是业务规则？

业务规则是系统所在领域制定的规则。

例如：

- 一门教学班有容量限制；
- 没有 override 时，学生不能选择时间冲突的课程；
- 某门课程要求学生先修另一门课程；
- Lucky Draw 只能在志愿提交截止后运行。

这些规则不是由 FastAPI 或 PostgreSQL 决定的。即使以后换成 Java 或其他数据库，规则仍然存在。

业务规则通常来自三种地方：

| 类型 | 含义 | 示例 |
|---|---|---|
| 已确认规则 | 有可靠、当前的来源 | 当前官方文件明确规定的规则 |
| 原型设定 | 为了完成实验，由我们自行定义 | Lucky Draw 使用固定随机种子 |
| 尚不确定 | 观察到但没有足够证据确认 | 学分下限是否在每次退课时立即检查 |

这个区分很重要。我们可以在原型中做决定，但不能把自己的决定说成学校的真实规则。

---

## 3. 什么是不变量？

不变量是：

> 无论系统经历多少合法操作，在我们指定的检查时刻都必须成立的条件。

最典型的不变量是：

```text
某教学班的已选人数 <= 该教学班的容量
```

假设教学班容量是 30：

- 已选 29 人：合法；
- 又有一名学生成功选课，变成 30 人：合法；
- 两名学生同时看到“还剩一个名额”，最后变成 31 人：违反不变量。

“不变量”比“功能”更严格。

“系统可以选课”只说明存在一个操作；“选课后永远不能超出容量”才说明这个操作必须维持什么正确状态。

### 一个重要细节：不变量需要检查时刻

以学分下限为例：

```text
学生总学分 >= 最低学分
```

它未必适合在所有时刻成立。学生可能需要先退掉一门课，再换选另一门课；两次操作之间可能暂时低于下限。

所以更准确的规则可能是：

```text
在选课阶段正式结束时，除非获得批准，
学生总学分不得低于最低学分。
```

这说明需求不能只写一个公式，还要说明它在什么时候生效。

---

## 4. 什么是用例？

用例描述一个参与者为了某个目标与系统发生的交互。

例如“学生选择教学班”：

```text
参与者：学生

前置条件：
- 学生身份有效；
- 选课阶段已经开放；
- 教学班存在。

主要流程：
1. 学生提交教学班编号和请求编号；
2. 系统检查重复选课、容量、时间冲突、先修课和学分；
3. 系统尝试创建选课记录；
4. 系统返回最终结果。

成功结果：
- 生成一条选课记录；
- 教学班占用名额增加；
- 请求状态显示成功。

失败结果：
- 不生成选课记录；
- 不占用名额；
- 返回可以理解的失败原因。
```

用例主要描述“过程”；不变量描述“过程结束后绝不能被破坏的状态”。

---

## 5. 什么是验收标准？

验收标准回答：

> 我们如何客观地证明这个需求已经完成？

不够好的写法：

```text
系统应该正确处理并发。
```

它无法被直接验证。

更好的写法：

```text
给定一个容量为 1、当前无人选择的教学班，
当 20 名不同学生同时提交选课请求时：

- 最终恰好有 1 条有效选课记录；
- 其余请求返回容量不足；
- 教学班的已选人数为 1；
- 数据库中不存在重复记录。
```

这段描述将来几乎可以直接变成自动化测试。

验收标准通常使用这种结构：

```text
给定（Given）：测试开始前的状态
当（When）：发生什么操作
那么（Then）：应该观察到什么结果
```

---

## 6. 架构决策不是业务规则

下面两句话性质不同：

```text
系统不能让教学班超出容量。
```

这是业务正确性要求。

```text
系统使用 PostgreSQL 行锁避免超选。
```

这是实现方案，也叫架构决策。

我们以后可能发现乐观并发控制更合适，并替换行锁，但“不允许超选”仍然不变。

可以把它们理解为：

```text
需求：要保证什么
架构：准备怎样保证
代码：具体如何实现
测试：怎样证明真的保证了
```
